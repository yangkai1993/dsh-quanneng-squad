## 二、三选一裁决建议

### 选项 A：保持现码（FAIL_ON_UNKNOWN_PROPERTIES=true）+ 登记与 DOC:537 的规范偏差
- 契约影响面：api-contract.md §5:61-65（裁定理由重写为「对 DOC:537 的主动偏差登记」）；§10 新增 K5 条（规范原文 DOC:537 ↔ 口径=偏差登记 ↔ 锚点 JacksonStrictConfig.java:22 ↔ 机器断言 compliance:K5）；§11 D-3 行 :116 改述为「未知字段拒绝已落北向（F5 已闭合），登记为对 DOC:537 的契约级偏差」。§2 无行变更（字段权威表不动）。
- 测试影响面：零改动。现依赖 400 行为的测试 grep 实测（gateway-java/src/test 全树）：
  - `north/GS3RecheckFixesTest.java:103` f5_unknownFieldIsRejectedWith400（:106 ghostField 探针 → 期望 isBadRequest）——唯一直接锚点；
  - `north/GS3RecheckFixesTest.java:71-80` f3 缺 M 字段（400 走 bean-validation，与未知 key 无关，仅同文件相邻）；
  - `north/SnControllerTest.java:53-59` invalidRegionRejected（400=PARAM_INVALID，校验路径，不依赖本开关）；
  - `north/Cr004GatesTest.java:142-148` (d) 缺 orderId 400（同上，bean-validation 路径）。
  结论：真正被本开关锁死的只有 f5 一例；Node 对照 tests/gateway.test.js:66-69 是南向投影丢弃断言（junkField 不出域），双端本就分域，不冲突。
- 安全面分析：
  - 严格拒绝是 fail-closed 面（application.yml:59 degrade=fail-closed 同哲学，契约 §5:65 已论）：未知 key 不可能携带未被校验的语义进入投影/出域签名体（F3 投影白名单是更强防线），400 只是把歧义前移给调用方。
  - 与 TK-60-01 入站验签链的交互（SnController.java:103-126 实读顺序：raw bytes → parse(:114) → bean validation(:123) → verifyInbound(:130) → flow.handle）：未知 key 触发的 400 发生在验签**之前**。含义双向——①攻击者无需有效签名即可探测「哪个字段名被接受」（错误回显当前为固定 msg，不回显 key 名，无信息差可放大，探测增益≈0）；②若银联侧因前向兼容在签名体里加入新数据元，报文在验签前即 400，不会产生「验签过但语义歧义」的中间态。TK-60-01 链路不受本选项影响（parse 在 verify 前，入站验签消费的是 raw bytes 而非反序列化对象，InboundSignSupport/InboundVerifyTest 全部按 raw body 签名）。
  - 残余风险：银联真实联调若发来带新增数据元的合法报文，我方 400 → 交易可静默损失（对账台账无此笔，因未进 flow）。需 E 项外部确认（银联是否会先行加字段）。
- 建议项与理由：作为兜底项保留。优点=零测试/零代码改动、fail-closed 哲学一致；缺点=直接违反规范明文 DOC:537，银联侧一旦加字段即断业务，偏差须在 §10 显式登记并留 E 项，合规审计层面永远挂红。

### 选项 B：改丢弃语义，对齐 DOC:537
- 契约影响面：§5:61-65 裁定行整体改写为「北向丢弃未知 key，对齐 DOC:537」；§2:43 bizMethod/appId X 档行需联动改述（现 X 档依赖拒绝语义，改丢弃后 X 档须改为「入口显式剥离或保留 D-2 静默吞例外」——即 X 档语义被本选项弱化，需单独 CR 澄清）；§10 K5（若 A 未先建）不必建，改为在 §11 撤销 D-3 中「未知字段拒绝」子句。§2/§3/§4 其余行不动。
- 测试影响面：负向翻转，f5 直接报废：
  - `GS3RecheckFixesTest.java:103-108` f5_unknownFieldIsRejectedWith400 必红（开关一翻即失败），需重写为「ghostField 存在 → 200 且不出域」（对齐 Node tests/gateway.test.js:68-69 junkField 断言语义）；
  - G-S3-final-2026-11-12.md F5 行与 G-S7.md:24 门禁记录成为历史口径（留档不改），verify 管线如含 F5 断言需同步（本轮 grep packages/dsh-quanneng-squad/scripts/*.mjs 对 unknownField/f5_ 0 命中，实测管线无此断言，影响面=仅单测）；
  - SnControllerTest/Cr004GatesTest 的 400 用例不依赖本开关，零改动。
- 安全面分析：
  - 验签绕过面：**不变**。入站验签消费 raw bytes（SnController.java:106 读原文，:130 验签），未知 key 丢弃发生在验签之后的反序列化阶段，攻击者仍必须持有效 SM2 签名才能让任何字段（含未知 key）进入处理；丢弃不创建任何新的免验签通路。DOC:314「验签通过后才能业务处理」由 TK-60-01 链独立保证。
  - 注入歧义载荷面：**此为选项 B 的真实代价**。丢弃语义下「别名/变形 key」（merchantId vs mchntCd、barCode vs barcode）被静默吞，调用方「以为传了、服务端从未看到」，成功脏数据风险回归——这正是契约 §5:64 引评审 R2/CR-004 E6 记录的原缺陷。缓解：投影层白名单（F3）保证未知 key 永不出域签名体，故注入上限=北向业务语义歧义（该笔交易字段缺失走 M 校验 400 或业务失败），不扩散到出域报文与银联侧。无验签/加密弱化。
  - 与 TK-60-01 链交互：verify 仍先于业务处理，丢弃不改变顺序；唯一新增面=「验签过 + 含未知 key + M 字段恰好齐全」的报文会静默通过并按已声明字段处理，审计侧建议保留 audit.body_sanitized（Sn26FlowService.java:140）观测。
- 建议项与理由：合规满分、业务前向兼容满分；但把 §5 已裁定的 fail-closed 方向整体反转，X 档语义联动弱化，且重启「别名静默吞」已知缺陷面。需两个 CR（§5 反转 + X 档澄清）与 f5 重写，变更面大于 A。

### 选项 C：可配置双模式（gateway.protocol.unknownFields=reject|drop）+ 默认对齐规范（drop）
- 契约影响面：§5:61-65 改为双模式条款（默认 drop=DOC:537 对齐；reject=调用方契约收紧开关，登记为可选 profile）；§2:43 X 档在 reject 模式下维持 400、drop 模式下走显式剥离；§10 新增 K5（规范原文 DOC:537 ↔ 口径=默认 drop ↔ 锚点=配置项+解析分支）；§11 撤销 D-3 中「未知字段拒绝」子句、新增 D-9「双模式落地」。api-contract.md 共涉 4 处（:61-65、:43、§10 表、§11 表）。
- 测试影响面：新增而非报废——f5 改造为 reject-profile 用例（保留 400 断言，@TestPropertySource 或测试 profile 固定 unknownFields=reject）；新增 drop-profile 用例（ghostField → 200 且出域报文不含 ghostField，对齐 Node junkField 断言）。现绿用例 grep 列表（同 A：GS3RecheckFixesTest.java:103、SnControllerTest.java:53-59、Cr004GatesTest.java:142-148）在默认 drop 下 f3/f5 两类均需按 profile 归位；ProfileGuardTest.java 不受影响（配置默认值必须给全，否则 D9 生产闸口会拒启——落码时 REQUIRED 项联动检查 application.yml）。
- 安全面分析：
  - 默认 drop 下安全面=选项 B 的全部结论（验签不受影响、注入上限=北向语义歧义、投影白名单兜底出域）；
  - reject 模式作为**调用方审计态**保留：联调期/合规审查期可切 reject，把字段歧义显式 400——双模式让 fail-closed 从「编译期唯一真理」降级为「运行期可选策略」，哲学从「防错」转向「可观测的可容错」，与 degrade 开关（application.yml:58-59）同构，团队已有先例。
  - 与 TK-60-01 入站验签链交互：配置只控制反序列化分支，raw-bytes 验签链（SnController.java:103-130）与顺序完全不动；两个模式都保证「先验签后业务」。
  - 新增风险面：模式切换本身成为配置面（profile 错配 → 生产误入 reject 恢复 400 风暴 / 误入 drop 掩盖调用方脏数据）；需 ProfileGuard 式启动期断言与部署文档登记。
- 建议项与理由：**本文建议采纳选项 C**。理由：①对齐规范明文（DOC:537），消除 §10 合规挂红与 E 项依赖；②保留 fail-closed 能力为显式开关，联调与审计期可用，不丢失既有防线；③与库内既有模式（reliability.degrade、spec.cateCodeExtra，config.js:53）配置化先例同构，落地成本低（JacksonStrictConfig 读取 gateway.protocol.unknownFields 分支配置 FAIL_ON_UNKNOWN_PROPERTIES + f5 profile 化，改动面 ≤3 文件：JacksonStrictConfig.java、application.yml、GS3RecheckFixesTest.java，另契约 §5/§10/§11 文档 CR）；④双端语义终趋同（Node 南向本就投影丢弃，tests/gateway.test.js:68-69 为既成断言）。
- 若采纳 C，转 CR 必带：契约 §5/§10/§11 四处改述、application.yml 新键、ProfileGuard REQUIRED 项联动评估、f5 profile 化 + 新增 drop 用例、E 项「银联加字段时序」确认。
